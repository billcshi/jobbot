# JobBot v0.6 Release Notes

## Overview

v0.6 is a foundational release that introduces **multi-user support**, **parallel pipeline execution**, **live pipeline monitoring**, and **application lifecycle tracking**. Profile data moves from YAML files into the database, and the pipeline is now fully concurrent with per-task cancellation.

## New Features

### Parallel Pipeline Execution

The pipeline now processes jobs **concurrently** within each stage instead of sequentially:

- **`asyncPool`** utility — generic sliding-window concurrency pool with AbortSignal support, progress callbacks, and tracked results
- Per-stage concurrency limits (configurable in `local/config.yaml`): extract=10, score=10, compose=5, audit=5
- **Per-user pipeline** — each user gets their own independent pipeline. Multiple users can run pipelines simultaneously without interfering
- **Global concurrency cap** (default: 50) prevents overwhelming the system when multiple users run pipelines
- Removed artificial `delay()` calls — the pool's concurrency limit naturally rate-limits
- **Automatic retry** for transient LLM errors (empty response, fetch failures) with one retry per job

### Live Pipeline Monitoring

The Pipeline page (`/pipeline`) now shows real-time progress of running pipelines:

- **Live status panel** — per-stage progress bars (extract/score/compose/audit) with ✓/✕/▶ counts
- **Task pool table** — lists every running task with job ID, stage, title/company, status, and elapsed time
- **Individual task cancellation** — cancel a single stuck job without stopping the entire pipeline
- **Cancel entire pipeline** — stop the global pipeline; already-running tasks finish gracefully
- Polls every second via `GET /api/pipeline/status`, auto-refreshes on completion

### Multi-User Mode

Jobs are **per-user** — each user discovers and adds their own job pool. Scoring, tailoring, and application tracking are all per-user:

- **`users` table** — user accounts (id, name, active, created_at)
- **`user_scores` table** — per-user job scores (score/tier/reason unique per user+job)
- **Per-user jobs** — `jobs` table has `user_id` column; same URL can be added by different users
- **`user_preferences` table** — per-user profile storage (candidate, preferences, answers as YAML text in SQLite)
- **Automatic migration** — existing v0.5 data assigned to a `default` user (id=1)
- **CLI commands**: `pnpm jobbot user-list`, `user-add <name>`, `user-switch <name>`, `--user` flag on score/list/run/tailor/compose
- **Web UI user switcher** — dropdown in the nav bar with add-user dialog; persisted via cookie
- Per-user score display on dashboard and job detail pages
- Delete protection — users can only delete their own jobs (403 otherwise)

### Application Lifecycle Tracking

Track each job through the full application lifecycle:

- **Status flow**: `draft → submitted → replied → interview → offer → accepted / rejected`
- **Job detail page** — new "Application Tracking" card shows current status, submission date, response type
- **Response buttons** — after marking as applied: "Replied", "Interview", "Offer", "Rejected"; after offer: "Accepted" / "Declined"
- **Dashboard filter** — "Hide applied" (default), "Show all", "Applied only"
- **API endpoints**: `POST /api/jobs/:id/apply`, `POST /api/jobs/:id/response`, `GET /api/jobs/:id/application`
- Events logged for every status change

### Profile in Database

Profile data moved from YAML files in `local/profile/` to the SQLite database:

- **`user_preferences` table** — stores candidate.yaml, preferences.yaml, answers.yaml as TEXT per user
- **`profile-store.ts`** — `readCandidate()`, `readPreferences()`, `readAnswers()`, `writeProfile()` with auto-row creation
- **`local.example/profile/`** removed — profiles no longer live on disk
- All LLM callers (score, tailor, cover-letter, market-data) read from database via `getActiveUserId()`
- Web UI profile editor reads/writes directly to `user_preferences` — no YAML files to manage

### Configurable Thinking & Concurrency

Fine-grained control over LLM reasoning and pipeline parallelism via `local/config.yaml`:

```yaml
deepseek_thinking:
  default: auto
  operations:
    score: disabled       # flash model, straightforward
    extract: disabled     # structured extraction
    tailor: enabled       # complex resume tailoring benefits from reasoning
    cover-letter: enabled # creative writing benefits from reasoning
    audit-content: enabled
 
concurrency:
  global: 50              # max total concurrent tasks across all users
  per_user: 10            # max concurrent jobs per user pipeline
  stages:
    compose: 5            # pdflatex is CPU-heavy
    audit: 5              # pdflatex + vision API
```

- DeepSeek v4-pro `thinking` mode configurable per operation
- Scoring uses `deepseek-v4-flash` by default (faster, no reasoning needed)
- All `max_tokens` bumped to 16384 for extract/tailor/cover-letter/audit; 8192 for score

### Robust LLM JSON Parsing

A new `parseLLMJson()` utility replaces raw `JSON.parse` across the entire codebase:

- Handles **markdown code fences** (` ```json ... ``` ` or ` ``` ... ``` `)
- Extracts JSON objects/arrays **embedded within surrounding text**
- **Debug dump** on failure — prints raw LLM response to stderr for troubleshooting
- Handles `reasoning_content` overflow — detects when DeepSeek's chain-of-thought consumes the token budget, throws a clear error

### Audit Improvements

- **Attempt tracking** — audit feedback files now record `attempt` counter (1–3)
- **Terminal failure status** — after 3 failed attempts, job status is set to `audit_failed` (not looped back indefinitely)
- **Feedback persistence** — compose reads the audit feedback file for retry context; audit overwrites it on each failure. After a passing audit, the feedback file is retained (allows re-compose with audit context if desired)
- **Per-job directory** — audit.json, audit-feedback.json, and page images all under `local/resumes/<jobId>/`

### Pipeline UI — Interactive Stage Controls

The job detail page now has interactive pipeline controls:

- **"Run Pipeline" button** — runs the full pipeline for a single job via `POST /api/run` with `{jobId}`
- **Clickable pipeline stages** — click any stage (Extract/Score/Compose/Audit) to restart from that point. Past stages show "Restart from [Stage]", current stage shows "Re-run [Stage]"
- **`POST /api/jobs/:id/run-from`** endpoint — resets a job to before a target stage and runs ONLY that job through the pipeline (unlike `/api/run` which processes all eligible jobs)

### Committee Audit System

The single content audit reviewer is replaced by a **committee of 3 independent reviewers**, each with a distinct perspective:

| Reviewer | Weight | Focus |
|---|---|---|
| ATS Screener | 30% | Keyword match, ATS compatibility, requirement alignment |
| Hiring Manager | 40% | Experience quality, impact quantification, competitive position |
| Format Reviewer | 30% | 1-page check, structure, readability, LaTeX artifacts |

- Reviewers run in parallel via `Promise.all`
- Scores are weighted-averaged; individual reviewer scores displayed (e.g., `ATS Screener 55 | Hiring Manager 48 | Format Reviewer 90 → Overall 63/100`)
- `Promise.allSettled` ensures one failed reviewer doesn't kill the committee
- Three dedicated prompt files: `prompts/audit-ats.md`, `audit-hm.md`, `audit-format.md`

### Customize — Aggressive LLM Resume Rewriting

The "tailor" step is renamed to **"customize"** and the LLM is now instructed to aggressively rewrite bullet points:

- **Merge, split, and rephrase** bullets to match the job description's language
- **Select which project to show** and customize its highlights for the job
- **Previous output fed to LLM on retries** — the LLM sees what it wrote before and makes targeted edits instead of starting from scratch
- Audit feedback moved to **top of the prompt** for prioritization
- Retries get **32K max tokens** (vs 16K for first attempt) for thorough fixes
- Thinking mode enabled for customization (`customize: enabled`)

### Resume Template — Major Fixes

- **No more icon rendering artifacts** — removed fontawesome5. Contact header uses clean pipe-separated text (`phone | email | linkedin | github`), fully ATS-parseable
- **Section ordering fixed** — Experience before Education for experienced candidates
- **Project name bug fixed** — placeholder renamed from `{{name}}` (collided with person's name) to `{{project_name}}`
- **Skills categorization** — added `Data Processing` category (Spark, Hadoop, Hive no longer mislabeled as "Databases")
- **Cover letter paragraph breaks** — fixed `\textbackslash{}n` artifacts in rendered PDF
- **10pt → 11pt** for better readability; tighter margins to compensate
- **Projects section** — now always shown (1 project, LLM-selected), with customized highlights

## Breaking Changes

- **Profile YAML files removed.** `local.example/profile/` is deleted. Profiles now live in the SQLite database (`user_preferences` table). The v0.5→v0.6 migration handles this automatically — existing profiles are NOT migrated (they were in `local/`, you need to re-enter or copy-paste).
- **`CANDIDATE_PATH` / `PREFERENCES_PATH` / `ANSWERS_PATH` exports removed** from `src/utils/paths.ts`. Use `readCandidate()` / `readPreferences()` / `readAnswers()` from `src/utils/profile-store.ts` instead.
- **Resume file layout changed.** Files are now under `local/resumes/<jobId>/` instead of flat in `local/resumes/`. Old files are not moved — re-compose to regenerate.
- **URL uniqueness is now per-user.** Two different users can add the same job URL. If you have scripts that rely on global URL uniqueness, update them to account for the user.

## Migration from v0.5

Automatic on next run (via `init-db` or any command that opens the database):

1. `users` table created, `default` user (id=1) created
2. `user_scores` table created, existing scores migrated to default user
3. `user_id` column added to `jobs`, `resume_versions`, `applications`
4. `response_type` / `responded_at` columns added to `applications`
5. `user_preferences` table created (empty — copy your profile YAML into the web UI)
6. All v0.5 commands continue to work; new features are additive

No manual steps required. The `default` user covers existing single-user setups.
